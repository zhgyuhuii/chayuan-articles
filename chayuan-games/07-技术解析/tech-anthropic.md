# Anthropic协议转换：Claude无改造上桌

放在几年前，把 Claude 接进一个只认 OpenAI 兼容协议的对弈系统，剧本通常是自己架一层代理，逐字段翻译请求，流式解析再对一遍事件格式，全跑通了才算完。察元竞技场把这个活揽进了产品里：Anthropic协议转换由本机模型网关自动完成，Claude 填上 Key 就能上桌，不改任何代码。这篇讲协议差异在哪、转换层怎么工作、为什么转换要放在网关。

## 两种方言：协议分裂的现实

85 家厂商目录里，绝大多数成员说的是同一种方言：OpenAI 兼容协议。DeepSeek、智谱 GLM、通义千问、Kimi 走兼容面，Google Gemini、xAI Grok、Mistral 提供兼容端点，Ollama、LM Studio、Xinference 这类本地推理也开兼容接口，OneAPI、NewAPI 一类中转更是把兼容协议当通用语。Anthropic 的原生协议是另一套：端点路径的命名、消息的装配方式、系统提示的位置、流式输出的事件形状，自成一格。

对开发者，协议分裂意味着每多接一家原生协议厂商，就要多维护一条请求链路、一套流式解析。对竞技场，模型一多，这笔账更不能用蛮力算。

从成本视角再算一遍。85 家厂商目录若逐家写适配，每家一条请求链路、一套流式解析、一轮回归测试，测试矩阵是厂商数、玩法数与对战模式的连乘。收敛到一种内部协议之后，矩阵坍缩成一列：引擎只测一种协议，网关只测转换层，Anthropic协议转换是额外要多测的那一段，范围收得很窄。

## 转换层怎么工作

本机模型网关里内置了一层转换：当请求目标是 Anthropic 原生端点时，网关把应用内部统一的 OpenAI 兼容格式请求翻译成原生格式发出去，再把返回的响应与流式事件翻译回兼容格式交给上层。上层因此只需要说一种话，Anthropic协议转换的全部复杂度被封在网关内部。

差异主要落在三处。端点不同：路径命名与版本组织是两套体系。消息装配不同：系统提示的安放位置、多段内容的组织结构，两边各有各的写法，转换层负责把一方的结构对齐到另一方。流式事件不同：兼容协议的增量片段与原生协议的事件序列对不上号，转换层把事件流逐段翻译，保证对局室里的思维链气泡在 Claude 身上照样实时滚动。

翻译是双向的两趟。去程把内部请求的端点、鉴权凭证、消息装配改写成原生格式；回程把响应体与流式事件逐段翻回兼容形状。对局室里那些实时滚动的思维链气泡、每手延迟与 token 用量，靠的正是回程翻译保住了事件流的时序与分段——翻丢一段事件，界面就缺一块信息。

## 无改造上桌的收益

收益是全链路的。对使用者，Claude 与 DeepSeek、GLM 的配置体验完全一致：选厂商、填 Key、测试连接、进对局室，没有任何「Claude 专属步骤」。对对局质量，出招协议、解析容错链、深度思考档这些机制对 Claude 一视同仁：它输出同样的 {move, comment} 结构，走同样的容错链，思维链气泡与每手延迟、token 用量展示照常工作。对维护者，Anthropic协议转换写一次，目录里任何原生协议成员都能复用同一条通道。

排障体验也拉平了。Claude 对局出问题，排查路径与 DeepSeek、GLM 完全一致：先看网关出口的请求与响应，再看解析链的处理结果，不需要为某家模型单独学一套调试姿势。对经常轮换模型的玩家，这份一致性省心不少。同一套 Key 校验、同一份协议画像、同一条容错兜底，Claude 在竞技场里就是一个普通选手，没有特殊化，也没有降级。

## 设计取舍：为什么转在网关

另一个选项是在引擎层给 Anthropic 单独写一条玩家链路。那样做的问题随厂商数量线性放大：每家原生协议一条链路，引擎里的协议分支越养越多，测试矩阵翻着倍地涨。收在网关转换，引擎与玩家层永远只见 OpenAI 兼容一种协议，网关之外的世界简单如初。

转换层放本机还有一层隐私与延迟的考虑：翻译发生在进程内，请求直达厂商端点，中间没有第三方中转服务器过手，Key 与对话内容不经过任何察元侧的服务。对每手都要求响应的对弈场景，这条直路比外挂中转少一跳，思维链气泡的流式体验也更跟手。

## 边界

转换层覆盖的是对局所需的消息往返与流式输出，不是 Anthropic 全量 API 面的逐字段翻译；厂商专有参数不保证一一透传，个别能力以实际对局表现为准。转换的正确性也依赖各家对自家协议的实现稳定，厂商改协议，转换层要跟着升级，0.1.0 阶段这一点由仓库的更新节奏承担。给从其他工具迁移过来的用户提个醒：在竞技场里配 Claude，不需要再找第三方代理服务，也不需要配系统级的环境变量——选厂商、填 Key 两步完事；旧工具里留下的代理地址若一并填进来，反而可能把请求引去别处，配置前先清理干净。还有费用那句老话：模型 API 的费用由你向厂商支付，Claude 的额度烧起来比多数国产模型快，挂锦标赛前先掂量一下。

### Anthropic协议转换对出招质量有影响吗

没有理由有影响。模型收到的对局信息与出招要求和其他厂商完全一致，转换只发生在传输格式层，不触碰提示内容与输出语义。真要说差异，那是模型本身的棋力与遵守协议的习惯问题，协议画像里能看出各自 JSON 格式遵守率的差别。

### 不走转换、直接用兼容端点行不行

任何 OpenAI 兼容端点都可以手填 baseUrl 接入，若你的中转已经把 Claude 包成兼容端点，走兼容面同样成立。但竞技场的默认路径是原生协议经网关自动转换，填好 Key 即用，不必自己折腾端点，两种走法选省事的那种就行。

### 除了 Claude 还有别的协议需要转吗

当前版本的重点就是 Anthropic 原生协议，85 家目录的其余成员与手填端点都在 OpenAI 兼容这一侧，不需要转换。协议版图如果变化，网关这一层就是承接变化的地方，引擎层不受牵连。

### 转换层出问题会波及其他模型吗

按设计不会。网关按端点分路，只有发往 Anthropic 原生端点的流量才进转换路径，OpenAI 兼容侧的请求不经过这段逻辑。极端情况某家原生协议变更导致转换失效，受影响的也只限该家，其余厂商照常对局。

协议问题看着不起眼，实则是「模型能不能同桌」的门槛。Anthropic协议转换的意义不在技术多炫，而在把门槛拆平：引擎说一种话，网关去迁就所有方言，模型只管上桌出招。工具该干的事，就该这样沉到看不见的地方去。
