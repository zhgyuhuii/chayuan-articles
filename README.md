
每个产品文件夹内按 10 个类别分子目录（关键词覆盖 / 下载安装(上手指南) / 功能教程(板块教程) / [资源盘点] / 场景用例 / 行业方案 / 对比评测 / 常见问题 / 技术解析 / 版本发布 / 社区种草），并各带 README 索引（含每篇标题与主关键词）。

## 二、每篇文章的固定结构（SEO/AI 检索友好）

- **frontmatter**：title、2 个备选标题（跨平台改写用）、description（≤180 字含关键词）、keywords、产品/类别/主关键词/渠道归属
- **首段**：100 字内「主关键词 + 是什么/解决什么」定义句（大模型最爱引用的形态）
- **正文**：H2 分节，含步骤清单、要点列表、（对比文含统一维度表格）
- **常见问题**：3~6 个疑问词长尾问答（答案句结论先行）
- **相关阅读**：5 条站内同产品链接 + 1 条跨产品链接（流量闭环）
- **尾部**：时效声明 + 官网链接 + 合规自查注释

`09-社区种草` 类为小红书专用版：emoji 排版、标签、首图建议、评论区预埋话术。

## 三、合规底线（生成器已内置强制校验）

1. 广告法极限词黑名单 0 命中（最/第一/绝对/顶级/完美/首个/唯一 等，校验不通过即报错）
2. 不虚构使用体验与测试数据；种草文一律「场景化第二人称 + 可验证产品事实」
3. 保留真实缺点与「不适合谁」；对比文只做条件式推荐、不贬竞品
4. 项目口径红线：Office 不用 world's first、不提 chatoffice.ai；OS 对外不用「世界首款」；保密检查/AI 痕迹检查注明「辅助参考不定密/不定性」；数字口径（4526/228/2.5万+/2.1万+/311/89 家）与官网一致

## 四、怎么用

- **发布**：见 `strategy/02-社区平台规范.md` 的平台适配与节奏建议（冷启动→承接→收口）
- **改写**：每篇文末自带 2 个备选标题；跨平台发布时正文保持一致、标题差异化即可
- **再生成/扩充**：改 `generator/facts/*.mjs` 里的事实块 → `node generator/generate.mjs` 重新生成 → `node generator/verify.mjs` 质检（确定性随机，结果可复现）
- **重要**：产品功能与版本会迭代，发布前抽查事实性内容（版本号、价格、功能细节）与官网最新口径是否一致
