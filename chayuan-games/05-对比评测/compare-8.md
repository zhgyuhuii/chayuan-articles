# 模型中转与直连厂商：对局稳定性差异观察

同一个模型 id，有人一路顺稳，有人隔三差五撞上限流提示。差别常常不在模型本身，而在模型中转与直连的选择：直连厂商是一跳直达，经中转则是你和厂商之间多了一站。察元竞技场两种接法都支持，这篇把链路差异、限流表现和怎么用对局数据观察稳定性讲清楚，写给正在配模型被链路问题困扰的人。

两条链路的对照，先看表。

| 维度 | 直连厂商 | 经中转接入 |
|---|---|---|
| 请求链路 | 本机网关直达厂商，一跳 | 本机网关到中转再到厂商，多一跳 |
| 鉴权 | 厂商 API Key | 中转 Key，映射规则以中转官方说明为准 |
| 延迟构成 | 网络与厂商服务 | 厂商服务外加中转环节 |
| 限流表现 | 429 退避后重试 | 受中转与厂商双重策略影响 |
| 计费账单 | 厂商账单 | 以中转账单为准 |
| 观察入口 | 对局室延迟与协议画像 | 同一套数据，可两路对比 |

## 链路层数：每多一站多一分变量

直连的结构简单：竞技场的请求从本机网关出发，直达厂商接口。变量只有两个——你的网络和厂商的服务状态，出了问题好定位。

接入的灵活度是竞技场的明确取向：85 家厂商目录之外，任何 OpenAI 兼容端点都能手填，中转只是其中一种用法；甚至同一家厂商你可以同时配直连与中转两条条目，测试与日常分开用。

中转多了一站。OneAPI、NewAPI 这类中转端点，任何 OpenAI 兼容地址都能在竞技场里手填 baseUrl 接入，多模型聚合、统一记账是它们的方便之处。但每多一层转发，就多一层变量：中转服务的稳定性、它的上游配置、它的限流策略，都会叠在你的请求上。哪家中转做得怎么样，以其官方页面为准，这里不轻下结论。

## 429 与兜底：竞技场怎么扛限流

限流是云端对局绕不开的事。竞技场的处理是分层兜底：429 限流自动退避，等一等再重试；重试会把上下文回喂，保持局面连续；重试仍失败走启发式代走，能挡杀就挡、能吃就吃，麻将取缺门里价值较低的一张；同一玩家代走计数超限判负。设计目标很明确：一个模型的 API 抽风，不能卡死整局。顺带提醒，退避等待会体现在每手延迟里，看到延迟突然拉高先别急着怪模型，看看是不是撞了限流。

这套兜底对直连和中转都生效。区别在于触发概率：链路上多一层限流策略，触发退避的机会在结构上就多一分。这是结构推论，不是实测结论，具体频率看你自己的链路。

还有一层容错值得知道：重试失败后的代走不是乱走，启发式规则按局面挑合理动作，能挡杀就挡、能吃就吃；同时同一玩家的代走次数有上限，超限判负，防止某个模型一直出问题拖垮整场锦标赛。

## 用对局数据看链路

竞技场给了你观察工具，不用猜。对局室里每手延迟和 token 用量实时标注，同一家厂商直连和中转各打几局，延迟分布自己能比出来；协议画像会统计每个模型的出招习惯——JSON 格式遵守率、平均出招耗时——同一个模型换了链路后画像明显变化，问题多半在链路而不在模型。顺带说明，画像只统计你本机的对局样本，不上传也不共享，样本量靠你自己的对局慢慢积累。

如果你怀疑链路，最快的验证是控制变量：同一款模型、同一款玩法、同一台机器，只换链路各跑三局，把每手延迟记下来比一比。竞技场不替你下结论，但证据都给你留好了。

还有个实用建议：两条链路各配一个模型条目，起名区分开，锦标赛里各跑几局，数据比任何人的口头评价都可靠。你的对局数据全在本机，想怎么对比都行。

## 计费与账单的观察点

链路还牵着账单。直连的账对着厂商，用量与计费口径以各家官方页面为准；中转的账对着中转方，加价、套餐、换算规则各异，具体以其官方页面为准。竞技场本身不收任何中间费，软件 MIT 免费。

对账时有个交叉验证的小技巧：对局室里每手都标 token 用量，攒一段时间的对局记录再对账单，两边数字对不对得上，链路的透明程度自己心里就有数了。对局数据全在本机，想怎么核都行；竞技场不代理任何计费，也不读你的账单，两边数字对不上的排查起点在链路侧。观察节奏建议从短局开始：五子棋这类快节奏玩法单局消耗小，先跑通链路再上锦标赛，避免长局中途反复退避拖时间。

## 条件式推荐

在意链路简单、出了问题好排查、账单直接对厂商，选直连，Key 从 85 家厂商目录点选填入即可。

在意多模型聚合、统一记账，或者手上有现成的中转额度，选中转，OpenAI 兼容端点手填接入，稳定性用你自己的对局数据验证。

两头都配着用也行：重点对局走直连，日常批量观战走中转，哪路稳用哪路，数据说了算。

## 实话实说：三条边界

中转服务质量取决于服务商本身，竞技场管不了上游，接入前自己验证；退避和代走保证对局不卡死，但频繁触发的链路观赏性会打折；协议画像只统计你本机的对局样本，样本量小的时候结论要保守。

## 你可能会问

### 中转会影响对局结果吗

竞技场的胜负判定归本机纯逻辑裁判，链路只影响出招速度与成功率，不影响判罚。但频繁退避和代走会让过程变难看，间接影响体验。

### 怎么判断问题出在中转还是厂商

两条链路各打几局对比延迟与成功率，再看协议画像里同一模型的耗时变化，哪条链路数据异常就在哪条上排查。

### 中转的 Key 怎么填

和厂商一样进设置 ＞ 模型配置，手填 OpenAI 兼容的 baseUrl 加中转 Key，点「测试连接」验证通过即可。

### 直连一定比中转稳吗

不轻下结论。结构上直连少一层变量，但中转的稳定性取决于服务商，以其官方页面为准，最终用你自己的画像数据说话。

### 中转能看到我的对局内容吗

链路事实上能见到经过它的请求，这是中转的通用属性，敏感场景自行权衡；竞技场侧能保证的是 Key 只存本机、对局记录不出本机。还有一点：退避与代走只发生在单模型出招环节，锦标赛的排程、积分、匿名观战都不受链路影响。

链路是变量，数据是答案。中转有中转的方便，直连有直连的省心，谁适合你不用听人掰扯——配两条链路各打几局，延迟、退避、协议遵守率全摆在对局室里，事实会替你做决定。
