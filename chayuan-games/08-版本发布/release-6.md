# 工程质量验证：裁判单测与真机对局验证

一个让大模型对弈的产品，先要回答一个问题：凭什么信它的裁判？模型只出招、代码判胜负，那裁判代码本身的正确性就成了公平的根基。察元竞技场 0.1.0 发布时，把工程质量验证的整套做法一起亮了出来：单测打底、真模型端到端、真机界面验证三层递进，再加一道与察元AI OS 的同构护栏。这篇面向想看工程细节的读者，不聊玩法，聊这套系统凭什么被信任——如果你想知道 11 款玩法的规则实现可不可靠，这篇就是答案。

版本口径：0.1.0，2026 年 11 月开源完整版，MIT 协议，仓库 github.com/zhgyuhuii/chayuan-games，官网 aidooo.com。下述测试体系随仓库开源，不是闭门承诺。

## 地基：裁判纯逻辑零 IO

架构分三层：electron 主进程负责单实例、模型网关与 JSON 存档（写锁加热读）；src/arena/ 是引擎层，11 款裁判纯逻辑零 IO，外加对局引擎、LLM 玩家、TrueSkill 与开局库；src/app/ 是 React 19 加 Vite 7 的界面层，暗色竞技场风格，中英双语。胜负判定 100% 归代码，模型没有判罚权。纯逻辑零 IO 意味着裁判不联网、不读盘，判罚只依赖入参：同样的输入永远得到同样的输出。可复现，才谈得上可验证。

裁判有一份统一契约：createGame、seats、phase、pendingAction、apply、result、viewFor、suggestAction、anonymize。11 款玩法都按这套接口实现，viewFor 保证每个座位只看到自己该看的信息，anonymize 支撑观战匿名。接口收敛，测试才有统一的落点，11 款裁判可以用同一套姿势验证。

## 测试分三层

### 单元层：vitest 裁判单测

用 vitest 覆盖 11 款裁判的边界情形，测的就是容易错的地方：麻将的吃、碰、杠、胡，围棋的劫争，军棋暗棋的翻子，掼蛋的贡牌，都在用例里。vitest 跑起来快，日常改动随手验证，是这套质量体系里转得勤的一环。边界用例挑的都是规则最容易含糊的位置：吃、碰、杠、胡的先后顺序，劫争的回提限制，暗棋翻子的归属，贡牌的方向与张数——这些地方一错，整局的判定就站不住。除裁判外，玩家协议与网关也有单测，模型出招的解析、网关的协议转换，都是独立验证过的逻辑单元。纯逻辑零 IO 的设计在这里兑现：不吃网络、不碰文件，断言只对着规则真值。

### 端到端层：real-e2e 真模型

单元测试过了，还得看真模型在完整对局里的表现。real-e2e 用真实模型 API 跑端到端，从配置写库、开桌选模型，到完整对局与结算，一条龙走真数据。代价是消耗真实额度，所以按需执行，不挂在日常流程里空烧。它验证的是单测盖不到的组合问题：真实模型的输出千奇百怪，容错链在脏数据面前接不接得住，全链路通不通，都得真模型说了算。

### 真机层：cdp-verify

单元测逻辑，端到端测链路，界面操作则交给 cdp-verify：走 CDP 做真机 UI 验证，从 T1 到 T7 七个场景，在真实应用里跑关键路径。单元与端到端多数在无头环境里跑，这一层逼着系统在真实界面上把活干完，逻辑对、界面点不动这种事，靠它兜住。

## 出招链路的可靠性

模型出的招未必是干净的 JSON——思维链混在正文里、代码围栏包着答案、大括号缺半边，都是常态。出招链路为此做了一整条容错处理：先剥掉思维链文本，再剥代码围栏，然后抽大括号、补截断的尾巴、做空白规整，正则抽取还不行就在全文里按词边界扫「当前合法动作串」，只认合法清单成员，绝不产出非法着法。强模型可以走深度规则模式，按分析、结论、答案三段交卷：分析段推演候选着法线并覆盖攻防，结论段一句话收口，答案段交出合法着法。给模型的对局信息也有讲究：着法与事件历史优先于棋盘图示，合法步清单显式附上。链路上还挂着 429 限流自动退避与重试回喂；这条链的设计逻辑是尽量保住模型自己的意图：能从脏输出里捞回真实着法就不动它，捞不回才逐级降级，代走是保底，不是常态。全都失败时启发式代走顶上，能挡杀就挡、能吃就吃，麻将从缺门里挑价值低的一张，代走超限判负——单个模型的 API 抽风卡不死一局。

## 同构护栏：sync-check

察元AI OS 内置了同款竞技场，家族产品的规则必须一致，两边引擎层要求逐字节同构，sync-check 就是验证这件事的护栏。同一套规则在独立桌面版与内置版里不许出现两个版本，用户在哪儿玩都是同一副牌桌。同构的价值在一致：同一局棋换边跑，规则表现与判定结果应当分毫不差，不会出现「换个壳规则变了」的怪事。

## 已知边界

三条。一，real-e2e 跑真模型就真烧钱，额度预算自己掂量，日常验证以单测为主。二，单测覆盖不等于零缺陷，0.1.0 是早期版本，边界情形仍可能漏网，发现问题去仓库提 issue 比猜测可靠。三，弱模型的协议遵守率低，容错链与代走能保证对局推进，代价是那一手不是模型自己的想法，观赏性打折。测试体系也不是万无一失的保证：极端局面与意外输入仍可能跑出新问题，开源的意义就在这里——问题可以暴露，修复可以验证。

## 你可能会问

### 为什么可以相信裁判

三重理由：裁判是纯逻辑零 IO 的代码，不吃外部输入；11 款玩法的边界情形有单测覆盖；胜负判定与模型完全隔离，模型没有判罚权。规则对不对，代码和测试都摆在开源仓库里，可查可复现。

### 跑一遍测试要花 API 钱吗

单元测试不花钱，测的是纯逻辑。只有 real-e2e 会调用真实模型 API、消耗真实额度，因此它按需执行，日常验证不依赖它。

### 同构是怎么验证的

sync-check 护栏逐字节比对独立版与察元AI OS 内置版的引擎层，两边不一致就拦下来。引擎层的任何改动都必须过这道检查，保证同一规则只有一份实现。也就是说，独立版怎么判，内置版就怎么判，不存在双标。

### 普通玩家需要关心这些吗

不必刻意关心，但它们决定体验下限：裁判不冤枉人、对局不卡死、界面点得动，背后都是这套验证在撑。想深究的，仓库里测试代码全开放。

### 发现规则 bug 怎么反馈

去开源仓库提 issue，写清玩法、局面与复现步骤即可。0.1.0 是早期版本，规则与体验都会持续迭代，仓库与官网 aidooo.com 会同步更新。

裁判可信、链路扛造、双端同构，这三件事决定了竞技场是竞技场，而不是一场演示。0.1.0 把验证体系连同代码一起开源，规则对不对，欢迎自己 clone 下来查。
