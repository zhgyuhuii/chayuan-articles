# 服务自愈：服务链自愈

服务自愈的麻烦不在功能本身，在于信息散。本地服务多，全靠人盯不现实，自愈机制让小故障无感恢复。这篇把它收拢成一条能照着走的路径。

## 是什么与为什么

为什么要有服务自愈：本地服务多，全靠人盯不现实，自愈机制让小故障无感恢复。故障自愈的定位是服务链自愈：崩溃退避重启、配置异常回滚上一可用版本、端口被占自动顺延并让消费方重新发现；

入口、步骤、验证三段看清，这事就顺了。

## 操作步骤详解

按最短路径验证一遍：

遇到故障怎么办

1. 先等自愈机制工作（崩溃退避重启通常几十秒内完成）
2. 诊断入口可一键打包上下文
3. 转给智能体给出修复方案或直接处理
4. 诊断包可导出给人工支持

三类常见自愈场景

1. 模型服务崩溃：退避重启并恢复加载清单
2. 配置异常：回滚到上一个可用版本
3. 端口被占：自动顺延端口并通知消费方重新发现

## 这些坑和边界要知道

边界先摆在桌面上：

- 8GB 内存设备建议一次只加载一个对话模型，复杂任务受限
- 云端厂商模型调用需自备 API Key
- 暂不支持龙芯平台；本地不提供视频生成（视频生成走云端路由）
- Docker 云桌面、跨终端互联这类进阶形态需要一点动手能力

## 常见问题

### 自愈失败怎么办？

自愈有重试上限，超限后服务进入停摆状态并在界面上标红。此时用诊断入口打包上下文，交给智能体处理或导出给支持人员。

### 配置回滚会丢我的自定义设置吗？

回滚只针对异常的服务配置（模型清单、端口映射这类），用户数据与个人设置不在回滚范围内。

### 端口自动顺延后，外部配置会失效吗？

消费方（智能体、加载项）通过服务发现拿端口，会自动跟到新端口；只有手写在外的固定端口配置需要同步改。
