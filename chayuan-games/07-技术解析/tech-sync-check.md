# 引擎同构护栏：双仓库逐字节同构怎么守

一套代码养两个宿主，福气在后头，麻烦也在后头。察元竞技场的引擎层 src/arena/ 同时活在两个地方：独立桌面版里，以及察元AI OS 的内置竞技场里，两边逐字节同构——不是「功能一致」，是文件内容一字不差。承诺下到这个份上，靠自觉是守不住的，得有机器盯着：scripts/sync-check.mjs 就是这道引擎同构护栏。这篇讲双仓动机、校验机制与冻结策略。

## 双仓动机：一个引擎，两个住处

先说为什么会有两个仓库。同一套引擎有两个宿主：独立桌面版是 MIT 协议的开源应用，谁都可以装来单玩；察元AI OS 是 AGPL-3.0 的系统产品，竞技场作为内置应用长在里面。两个产品各自发版、各有节奏，引擎层是它们共享的同一份逻辑——11 款裁判、对局引擎、LLM 玩家、TrueSkill、开局库，全在 src/arena/ 这一层。

这个布局的回报很实际：规则修一次，两个宿主同时受益；用户在哪个宿主里玩，见到的都是同一套规则真值。但回报的另一面是义务：改引擎必须双侧同步。任何一侧单独动了引擎层，「同一套规则」的承诺当场作废——用户在独立版里看到的胡牌判定，与在 OS 里看到的不一样，这种分歧对一个以判定权威立身的应用是致命的。

## 漂移怎么发生

漂移不需要恶意，只需要忙碌。典型剧本：独立版这边有人修了一个劫争判定的边界 bug，改完测过，提交；OS 那边的引擎副本不知道这件事，下一次同步之前，两个宿主各带各的规则活着。更隐蔽的是无意的漂移：一侧做重构，顺手改了变量名、调整了文件组织，行为没变，文本变了——逐字节同构照样告破。

还有一类漂移与代码无关：同一份代码跑在不同宿主环境里，依赖版本、运行时的差异带来行为分歧。这超出了文件校验的射程，护栏管不了，要靠宿主侧各自的测试去兜。

## 校验机制：sync-check 怎么盯

护栏的做法朴素而彻底：scripts/sync-check.mjs 把两个仓库里的引擎层文件逐个比对，逐字节校验，任何一处差异——多一个空格、改一行注释——都会被点名报出来。

为什么是逐字节而不是「对行为」？行为一致性听着合理，实际上无法机器验证：要证明两份代码行为一致，得枚举所有输入，做不到。逐字节是强得多的承诺，也是机器可验的承诺：文本相同，行为必然相同。校验跑在什么时候、挂不挂在持续集成里，以仓库的工程实践为准，但它作为验收门槛的地位是明确的：引擎层的改动，双侧同步完成、护栏跑过，才算闭环。

跑一次校验的成本也低：纯本地的文件比对，不联网、不构建，几秒出结果。便宜的护栏恰恰是最容易坚持到底的那种——许多好的工程约定败在执行太麻烦，sync-check 把执行成本压到了没有借口的程度。

护栏的管辖范围也要说清：它守的是引擎层，不管界面与宿主代码。两侧的 UI、网关、产品功能本来就该各自演化，那不是同构承诺的领土。

## 冻结策略：动一次付两次的代价

逐字节同构落到日常开发上，变成一条纪律：引擎层非必要不动。

这不是惰性，是算过账的。引擎层每动一次，双侧都要落笔、都要测试、都要过护栏，改动成本是单仓的两倍。于是「什么该进引擎层」就有了明确的门槛：规则真值相关的才进——判定、计分、合法动作、终局；界面表现、提示文案、宿主特性，一律挡在引擎层之外。引擎层因此保持小而稳：冻结不是不进化的意思，是进化必须双侧同步、逐字节对齐之后再落笔；把可长可短的部分留给宿主层自由生长，必须铁板一块的部分焊死在 src/arena/ 里。

这套分法还有个隐性收益：开源贡献者提引擎相关的改动时，门槛清清楚楚——动了引擎就带上另一侧，跑 sync-check 自证；只动宿主侧，则不必关心同构。

## 设计取舍

读者可能会问：为什么不把引擎做成共享依赖包，两个仓库各自引用，从根上消灭拷贝？这条路要引入跨仓的包管理与版本协调，两个宿主的运行环境、许可协议、发版节奏都要对齐到同一个依赖上，约束链条长。当前选择的方案是拷贝加护栏：多付一份存储与一次同步的功夫，换来两个宿主零分歧、一台机器就能验货。两种方案各有适用的组织形态，竞技场的取舍把简单与可验证放在了前面。

sync-check 与测试的分工也值得一句：测试验证行为符合预期，护栏验证文本两侧一致。测试全绿的两份不同代码，依然破坏同构承诺；反过来，逐字节一致的代码天然行为一致。两者互补，缺一不可。

## 边界

三条实话。护栏是事后验证：忘了跑，漂移就溜进去了，这道闸的可靠性建立在「引擎层改动必跑」的流程纪律上，机器只负责把漏网之鱼揪出来。同构只覆盖引擎层，宿主侧的差异要各自维护，两边 UI 的功能差异属于正常现象，不要拿同构的标准去要求界面。另外，逐字节同构对环境差异不设防：Node 版本、Electron 版本、操作系统差异引发的行为分歧，文件校验无能为力，那要靠各宿主自己的测试与真机验证兜底。

### 引擎同构护栏和单元测试重复吗

不重复。测试管行为对不对，护栏管两边是否一模一样；两份行为正确但文本不同的代码，测试全绿，护栏照样报警。一个管正确性，一个管一致性。

### 我给独立版提的引擎改动会影响 OS 版吗

会。动了 src/arena/ 的改动按仓库约定需要双侧同步，提交前跑一遍 sync-check 自证同构；只动界面与宿主侧的改动不受此限。

### 为什么不干脆合成一个仓库

两个宿主的许可协议与产品节奏不同，合仓会把两个产品的发版绑在一起。双仓加护栏的方案里，产品各自独立，引擎共用一份逻辑，边界清楚。

### 逐字节同构连注释和空格也算吗

算，逐字节就是字面意思：注释、空格、换行符都在校验范围内。这让规则简化到没有争议——不存在「重要差异」与「无关差异」的辩论，一致就是一致。

引擎同构护栏守的不是某个功能，而是一个承诺：不管你从哪个门进来玩，棋盘后面的规则是同一份。sync-check 这个脚本体量不大，管住的却是两个仓库之间最容易烂掉的那条缝——工程里许多信任，就是靠这类笨而彻底的校验撑起来的。
