# 本机模型网关：随机端口与路径令牌鉴权

先问一个扎心的问题：你在各类 AI 应用里填过的 API Key，都存在哪些进程的内存里？多数应用答不上来。察元竞技场的答案是明确的：Key 只出现在主进程一侧，所有模型流量走一个口子——本机模型网关，监听 127.0.0.1 随机端口，用 path-token 鉴权。这篇拆开讲这套设计防的是什么、怎么防、代价是什么。

## Key 与流量：桌面应用的两块心病

接 85 家厂商目录的模型，应用绕不开两件事：Key 存哪，流量怎么走。存得散，暴露面就大——渲染进程一份、配置文件一份、日志里再来一份，泄露只是时间问题。流量走得乱，排查就难——每个模块各自直连厂商端点，限流、失败、协议异常散落在四面八方，出了问题无从下手。

本机模型网关把两件事并成一件事来解：流量收口到一处，Key 也就顺势只需要待在这一处。

## 随机端口：门牌号不提前挂出来

网关监听 127.0.0.1，只有本机能访问，局域网里的其他设备根本看不见它。端口用随机分配而不是写死一个数字，用意有两层。固定端口等于在门上挂一块永久招牌，本机任何进程都能顺手扫一扫这个号在不在、通不通；随机端口每次启动换一个号，外部进程无从预判，端口撞车（被其他软件占了）的麻烦也一并消失。

当然，端口只是隐藏，不是鉴权。知道端口号不等于能进门，这才轮到 path-token。

回环绑定本身还有一层容易被忽略的含义：它把「网络可达」从网关的威胁模型里划掉了。局域网扫描、公网探测、相邻设备嗅探，这些针对桌面服务最常见的攻击面，在 127.0.0.1 面前统统无效——端口再好猜，数据包也从别的机器进不来。剩下要防的只有本机进程，攻击面从一张网收窄成一台机器上的若干个进程。

## path-token：端口之外的第二道门

路径令牌的做法：网关的访问路径里必须携带一段随机令牌，不带或带错的请求一律拒绝。它把「知道网关在哪」与「有权访问网关」拆成两个独立条件——本机的恶意或冒失进程即便撞见了端口，没有令牌也只能吃闭门羹。令牌由主进程自己生成、自己拼接、随应用运行而存在，不落在对外可读的固定位置，渲染进程与外部进程都拿不到。

这套双条件设计防的是本机侧的顺藤摸瓜：同一台机器上的其他应用、脚本、浏览器扩展，想借你的 Key 发请求，得同时凑齐端口与令牌两样东西。缺一样，请求在门口就被打发走。

## 单点出口的价值

所有模型流量从本机模型网关一个口子出去，好处是成体系的。协议差异收口在此：Anthropic 原生协议在这里自动转成 OpenAI 兼容格式，Claude 无改造上桌，引擎与玩家层只见一种协议。观测收口在此：哪家端点在限流、哪家响应慢，网关看得一清二楚，429 自动退避也据此运转，一个模型 API 抽风不会卡死整局。排查同样收口：模型请求出问题，先看网关这一处，不用在多个模块里翻日志。

连配置页的「测试连接」与「获取模型」也归口这条通道，不在外面另开旁路。这两颗按钮一个用 GET 校验连通性、一个用 POST 实拉模型清单，走法不同，出口是同一个，审计与排障时不必多追一条线。

退避的节奏也归这条出口管。某家端点返回 429 限流时，引擎侧自动等待再重试，重试仍失败走回喂与代走，这些策略都在网关观测数据的支撑下运转。单点出口的价值不只是安全，更是让整局的节奏控制有了统一的依据。

## Key 怎么存

Key 明文只存本机 userData 目录下的 arena/config.json，永不上传；配置写入带写锁，运行时热读取，改完即用。加密升级位已经预留，后续版本可以切换到加密落盘。这里得说实话：当前的落盘形态是明文，安全性建立在「本机 userData 目录只有你的用户账户可读」这层系统权限上，加密位落地之前，多人共用一个系统账户的机器要多留个心眼。

写锁与热读的搭配也值得一说。配置写入串行化，避免两处同时改 JSON 造成损坏；热读取则让换 Key、换端点这类操作在下一手对局立即生效。对挂机跑锦标赛的人，这个细节很实际：半夜发现某家限流严重，中途换一家不用停赛。

## 边界

随机端口加路径令牌的方案，防的是本机其他进程与局域网侧的顺手牵羊，不是密码学意义上的强隔离；拿到你系统账户权限的进程，理论上能读到 config.json，这是所有本机存储方案的共同边界。网关只服务模型流量，对局记录导出这类本地文件操作不经过它。另外，随机端口意味着外部工具想直连网关做调试，得先从应用侧获知端口与令牌——这是设计使然，不是缺陷，但做集成的人要知道这个门槛。还有一层要说明：网关不改变费用归属，模型 API 的账单永远来自厂商侧，网关只管把请求送到你指定的端点。

### 本机模型网关会把我的 Key 发到察元的服务器吗

不会。网关的出口直连你配置的模型厂商端点，察元侧没有中转服务器，Key 与流量都不上传。用 Ollama 这类本地推理时，整条链路甚至可以完全离线。

### 随机端口会不会和别的软件冲突

随机分配本身就是为绕开冲突设计的：每次启动从可用端口里取一个，撞上被占端口的概率趋近于零，也免去固定端口被抢占后应用起不来的老问题。

### path-token 会不会泄露到日志里

令牌由主进程持有与拼接，设计上不进入对外可读的固定位置。真正的风险点在你自己的终端历史或抓包工具——调试时把带令牌的完整路径复制得到处都是，属于本机自我管理问题，网关替你防不了这一层。

### 换了网络环境网关还工作吗

工作。网关绑在回环地址上，不依赖外部网络环境；用 Ollama 等本地推理时整条链路离线可用，云端模型只要求本机能访问厂商端点。换网络、开热点、断网打本地局，都不影响网关本身。

本机模型网关的这套设计，思路是把信任半径压到最小：流量一个口、Key 一处存、门上两道锁。它不承诺解决一切安全问题，但把桌面应用接模型最常见的几条泄露路径提前堵上了。对一款把「数据不出本机」当立身之本的开源产品来说，这道工序不是加分项，是及格线。
