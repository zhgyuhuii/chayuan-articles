# 竞技场测试体系：从裁判单测到真机验证

一局棋的胜负由代码裁定，那么代码自己由谁裁定？这道题的答案，写在测试目录里。竞技场测试体系的特别之处在于分层逻辑：越接近规则真值的代码测得越密、跑得越勤，越依赖外部世界的部分测得越真、跑得越省。从裁判单测到真机验证，四层测试加一道同构护栏，各有各的岗。这篇逐层拆开看。

## 为什么一款裁判型应用最怕 bug

普通应用的 bug 顶多是功能不好用，竞技场的 bug 会直接制造冤案：该胡的没判胡、劫争的循环算岔、边池的筹码分错，用户看到的就是一次错误的胜负——而胜负是这款产品拿去排位、进天梯的硬通货，冤案会顺着 TrueSkill 一直污染到榜单。所以测试投入的重心清晰可辨：规则真值层测得最狠。

## 单测分层：裁判、协议与网关

裁判层。11 款玩法的裁判是零 IO 的纯逻辑代码，vitest 对着规则边界猛测：麻将的吃、碰、杠、胡，围棋的劫争，军棋翻翻棋的翻子与暗棋规矩，掼蛋的贡牌，德州的边池，每款玩法各有各的刁钻角落。这些边界条件的枚举工作量不小，但一次写完长期受益——规则代码改动频率低，测试的保护期很长。零 IO 的回报在这一层兑现得彻底：不启动界面、不连网络，毫秒级跑完一轮，改一行规则立刻知道有没有砸到别处。裁判契约的每个方法——开局、座位、行动请求、落地、终局、视角、建议——都在可测的射程内。

协议层。LLM 玩家的出招协议与解析容错链同样有单测守着：各种畸形输出样本喂进解析链，剥围栏、补截断、回捞认领，每一级的行为都有断言盯着。模型会怎么说话无法穷举，但见过的姿势必须不再翻车。

网关层。本机模型网关的测试覆盖三块：path-token 鉴权（不带令牌、带错令牌的请求必须被拒）、双口径模型列表（GET 校验的静默回退、POST 实拉的严格不回退，各自的行为边界）、错误透传（厂商侧的报错要如实到达界面，不能吞掉变成无声失败）。

## real-e2e：真模型端到端

单测能证明逻辑对，证明不了真实厂商配合。real-e2e 用真 Key、真模型跑完整对局：从出招请求到解析落子到终局判分，整条链在真实世界里走一遍。它专抓单测够不着的东西：厂商真实输出的千奇百怪、流式事件的实际形状、限流与超时的真实节奏。

代价也写在名字旁边：消耗真实额度。所以它是按需跑的测试，不进日常快速回归——每次跑都在烧自己的钱，跑之前先想清楚要验证什么。这也是一个诚实的工程取舍：真世界的测试有不可替代的价值，但价值要按次计价。

## cdp-verify：真机 UI 验证

界面层的验证交给 cdp-verify：用 CDP（Chrome DevTools 协议）驱动真实的 Electron 界面，按 T1 到 T7 的场景清单做真机 UI 验证——配置模型、进大厅、开对局这些关键交互，自动化替人点一遍，界面行为直接在真实应用里核对。CDP 是浏览器与 Electron 共用的调试协议，拿它驱动界面等于用同一套自动化语言跟真实应用对话：脚本按下按钮、等待界面反馈、核对状态，人手动点一遍要十分钟的关键路径，脚本几十秒走完，而且每次走得一模一样。具体场景明细以仓库清单为准，方向是明确的：单元测试证明不了「用户点下去真的能用」，真机验证补的就是这一段。

## 分层的分工与一道护栏

把几层排开，是一张按代价与保真度排列的表：裁判、协议与网关的单测，快、免费、天天跑；real-e2e 慢、花钱、按需跑；cdp-verify 保真但依赖真机环境，守住关键路径。测试体系之外还有一员——sync-check 同构护栏，它不测行为，专守独立桌面版与察元AI OS 内置版的引擎层逐字节同构，保证两个宿主跑的是同一套被测过的规则。行为测试与文本校验互补，缺了哪一边，另一边的证明力都打折。

## 设计取舍

为什么裁判测试排在前头？错误代价不对称：裁判错一次是一桩冤案，网关错一次可能只是一次重试。测试资源跟着错误代价走，规则真值层自然权重高。

为什么 real-e2e 不做成常规回归？额度是硬约束，厂商服务还带天生的不确定性——偶尔一次红，未必是产品的问题，可能是厂商抽风。把它放进日常回归，红绿灯就失去了信号价值。

为什么 UI 验证走 CDP 而不是截图比对？截图只能证明「长得对」，证明不了「交互通」。竞技场的核心体验在对局室里那一路交互：出招、气泡、判分、复盘，这些都是过程性的，要真机跑给 CDP 看。

## 边界

三条实话。测试覆盖以仓库为准，覆盖不等于无 bug：11 款裁判的边界再密，也密不过真实对局的分岔，确定性架构保证的是「错了可复现可修」，不是「永不错」。real-e2e 的红绿要会读：厂商侧抖动造成的失败，重跑一次、换一家模型就能分辨。厂商协议变更不在任何测试的预判范围内——85 家厂商哪天改了接口，测试要跟着现实修，这是接外部世界的代价。

### 竞技场测试体系跑一次要花钱吗

分层看：单测与 sync-check 本地跑，零成本；cdp-verify 真机跑，不烧额度；real-e2e 用真模型真 Key，按次消耗你自己的 API 额度，按需跑。

### T1 到 T7 场景都验证什么

那是 cdp-verify 的真机 UI 验证场景清单，方向是配置、对局等关键交互路径。具体场景明细以仓库里的清单为准，跑一遍就知道每条验什么。

### 测试全绿就能保证裁判不误判吗

不能，也不必这么许诺。全绿说明已知边界都有断言守着；未知的边界要靠开源社区的实际使用去撞，撞出来就是一条新测试用例。确定性架构的价值在于错误可复现、可定位、可修。

### 我贡献代码要跑哪些测试

按改动层级来：动引擎层记得双侧同步并跑 sync-check，动裁判补对应玩法的单测，动网关跑网关测试，涉及界面的改动用 cdp-verify 验关键路径。

### sync-check 算不算测试体系的一部分

它不测行为，只验两个宿主的引擎层文本一致，严格说不算传统意义的测试，更像一道验收门槛。但它与测试互为犄角：测试证明规则对，护栏证明两边跑的是同一套规则，缺了谁另一边的证明力都打折。

竞技场测试体系没有炫技的成分，四层各自的岗位都来自一个朴素的判断：什么代码错了最疼，就把测试的火力压在哪里。裁判测得最狠，协议次之，真世界按次验证，界面真机点过——胜负归代码，代码归测试，这条链走通了，天梯上的名次才值得当真。
