# OpenAI兼容端点测试：用对局压一压你的中转

用过 OneAPI、NewAPI 这类中转的人，大概都被坑过：商家页面写得漂亮，声称全模型直连、无限速；你单发一条「你好」，响应飞快；真把业务挂上去，高峰期延迟飙升、请求动不动被限。OpenAI兼容端点测试这件事，单次 ping 根本测不出门道——你得模拟真实负载持续压。察元竞技场提供了一种不太正经但相当有效的测法：让中转背后的模型连着打几个小时棋牌，每手棋都是一次带上下文、要结构化输出的真实请求，稳定性好坏，一局对局比一百次心跳检测诚实。测完你手里还多出一份带数据的观察记录，找服务商扯皮也好，续费也罢，底气都足一些。

## 这件事原来的难处

测中转，难在「轻量测试测不出真问题」。

单发请求测的是理想态。一条短消息往返一次，延迟两秒以内，商家看起来无可挑剔。但真实业务是长上下文、高频次、持续数小时，中转的排队、超卖、偷偷限速，全藏在这些维度后面。

自写脚本压测成本高。要模拟带上下文的持续请求、统计成功率与耗时分布，写一套下来半天没了，而且测出来的是裸指标，你还得自己解读；脚本跑完只有数字，没有场景，数字异常时你很难向别人解释它意味着什么。

更麻烦的是没有对照组。延迟多高算正常、限流几次算离谱，没有参照系，测了也白测。

计费端还有猫腻可藏。同样的请求，有的中转按十倍折算 token 再入账，账面数字看着不高，折回原厂对一对才知道亏了多少——裸测试照不出这类问题。

## 用对局压一压你的中转

第一步，把中转接进来。装好察元竞技场，进设置 ＞ 模型配置，不选内置厂商，直接手填 baseUrl 指向你的中转端点——任何 OpenAI 兼容接口都能接，OneAPI、NewAPI 搭的中转都一样。填上 Key，先点「测试连接」，它按校验 Key 的思路走一遍，通不通马上知道。再点「获取模型」，这一步严格实拉：用你当前填写的地址与 Key 真实请求该账号可用的模型全列表，拉不出来不糊弄。注意，这里本身就是测试点——列表拉取失败或残缺，说明中转对 /v1/models 的透传有问题，直接记一笔。

第二步，上负载。选中转背后挂的模型开机机观战或小型锦标赛，让它们连续对弈。棋类对局每手都要喂着法历史与合法步清单，模型还要按 {move, comment} 协议回结构化输出，这比闲聊重得多。打法上建议短局多打：几十局五子棋比一场超长围棋更能暴露稳定性问题。负载口径也要固定：玩法、局数、时段都一致，两轮数据之间才有可比性。

第三步，边打边看三个指标。一是每手延迟：对局室名牌旁实时显示，高峰时段与低谷时段各跑一轮，延迟曲线一对比，中转的时段画像就出来了。二是 429 出现频率：应用遇限流会自动退避重试，整局不会断，但从节奏上你能明显感觉到哪些手被卡了。三是代走触发：请求接连失败时，系统按启发式帮模型出招，同一玩家代走超限还会判负——如果你看到某座位频频被代走甚至直接判负，中转在丢请求，别怀疑。三个指标都落在对局记录里，比肉眼印象经得起追问。

第四步，出报告。打完看协议画像：JSON 格式遵守率与平均耗时按模型分列。格式遵守率异常低，可能是中转偷偷换了低价模型顶包；平均耗时明显高于厂商官方口径，说明中转加了缓冲。不同时段、不同中转各跑一轮，把画像摆在一起，谁是直连谁是二道贩子，一目了然。报告里把对局时间、局数、玩法写全，这份材料拿去与服务商谈判或者申请换通道，都是实打实的证据。

想比两家服务商也简单：同一个模型分别走两家中转各跑一轮，其余条件全部不动，延迟与遵守率摆在一起看——中转之间的高下，比广告页可信得多。

补一个容易漏的观察点：token 用量与账单对账。对局室里每手都标着 token 用量，一晚打完总量是清楚的，拿这个数去对中转的计费记录，折算倍率公不公道，一比便知。

## 适合谁、不适合谁

适合：自建 OneAPI 中转想验收质量的运维、买中转服务怕踩坑的个人开发者、要给团队挑稳定通道的后端工程师；做 AI 应用要挑供应商的采购与架构师，也可以把这篇当验收流程用。不适合：要精确压测 QPS 与并发上限的人——对局是持续的单线程负载，不是并发压测工具，数字口径完全不同；也别把它当替代品，专业压测该用还得用。

## 常见疑问

### 能测 Anthropic 原生接口吗

竞技场统一走 OpenAI 兼容协议接入，Claude 的原生协议由本机网关自动转换。你测的对象只要是暴露了 OpenAI 兼容端点的中转，就能按这篇的方法来；只提供原生协议的通道，则要先过一层协议转换再测。

### 测出来延迟高怎么办

先分清是中转慢还是模型慢。同一模型直连厂商跑一轮对照，差值就是中转的加价。再分时段跑，高峰独有的高延迟是排队问题，全天高的高延迟是链路问题。测出来的数据记得存档，每季度复测一轮——中转质量是会变的，上次的数据救不了这次。

### 会烧掉多少额度

对局是真实请求，token 消耗比闲聊大，局数越多花得越多，这笔钱照常走你的中转计费。建议先用小额跑半天画像，再决定要不要拉满整周。控制成本的空门是选短局玩法，五子棋十几手一局，比长围棋省得多，暴露问题的效果还不打折。

### 和写脚本压测有什么区别

省事与真实感。脚本测裸接口，对局测的是「长上下文加结构化输出加持续数小时」的复合形态，还自带延迟统计、格式遵守率与限流退避的观察窗口，代价是口径不如压测工具精确。

中转商家的话术千篇一律，请求的轨迹千差万别。与其听信页面上「直连、无限速」的承诺，不如让模型替你上一班岗：连打几小时棋，延迟、限流、掉包全都写在对局记录里。花一场对局的额度，买一份中转的体检报告，这笔账怎么算都不亏。
