# 429限流退避：对局不中断的重试策略

挂机跑锦标赛的人，怕的从来不是谁棋臭，是局跑到一半不动了。大模型 API 背后是一台台共享算力的在线服务，赶上高峰，厂商会礼貌地挥手：太挤了，等会儿再来——这个挥手就是 HTTP 429。察元竞技场把 429限流退避做成了对局引擎的自愈能力：限流被当作对局的天气而不是事故，等一等、重一发，不行就把失败的回复喂回去再要一次，实在走不通还有启发式代走接盘。一个模型的 API 抽风，不会卡死整局。这篇按限流场景、退避节奏、重试回喂的顺序，把这套策略拆开看。

## 限流为什么是竞技场的家常便饭

先看工况有多容易踩线。竞技场接的是 85 家厂商目录里的模型，每家的限流政策自成一套：有的按每分钟请求数卡，有的按每日 token 总量卡，有的按并发连接卡，免费与低价档位卡得尤其紧。对局形态又天然费请求：一手棋一次请求，锦标赛多桌并行，机机观战批量选模型，同一厂商在短时间内被连着敲门的场景司空见惯。

也就是说，429 不是罕见故障，是这款产品运行环境里的常态天气。把它当成异常去弹窗报错，挂一整晚的锦标赛会在半夜停下等你点重试；把它当成天气去适应，对局就能自己走出雨区。429限流退避的设计立场是后者：限流是节奏问题，不该由人来救。

## 429 到达之后发生了什么

顺着一次限流把时间线走一遍。请求从引擎层出发，经主进程的本机网关单点出口发往厂商端点；厂商返回 429，网关先看见——哪家端点在限流、限得有多频繁，网关这一侧一目了然，这是单点出口架构带来的观测红利。

接着进入等待。限流窗口通常以秒计，立刻原样重发等于往限流枪口上撞，多半换来第二个 429；等一段再试，让厂商侧的计数窗口翻篇。等待多久、重试几轮，属于退避节奏的调校范围，具体参数以仓库实现为准，方向是明确的：既不能激进到被厂商连续拒绝，也不能保守到一手棋干等几分钟、把全桌的对局节奏拖垮。

重试通过，对局继续，这一手没人察觉发生过什么。重试仍不奏效，就轮到回喂出场。

## 重试回喂：把失败当上下文用

普通的重试是原样重发，回喂多走了一步：对局引擎把失败后拿到的回复——可能是一条报错，也可能是那份没能解析出招的残次输出——作为上下文喂回给模型，再要一次回答。

这个动作的妙处在于给模型补了一句没明说的话：你上一轮答坏了。语言模型看得到自己前面说过什么，就有机会对着那份不合格的输出自我修正，而不是凭空再猜一次。对局信息里本来就附有合法动作清单，回喂等于让模型带着「上次没答对」的提示重新对照清单作答，解析链也重新获得一次干净输入。回喂是重试的强化版，不是一个独立环节：先等一等再要，要的时候把失败的回复一并递回去。

## 退避走完仍不行：交给兜底链

回喂之后仍拿不到可用的招法，说明这家厂商此刻已经不只是慢，是近乎失能。按既定的顺序，解析容错链与合法动作回捞处理文本，重试回喂处理沟通，它们一路走完仍无合法招，才轮到启发式代走接手：能挡杀就挡，能吃就吃，轮到麻将就从缺门里挑价值最低的一张。代走产出的动作由裁判担保合法，对局继续；代走计数记在该玩家名下，超限判负。

这条链的完整含义值得说透：限流从头到尾没有资格终结一局棋。它可以让某一家模型的出招变慢、变差，极端情况下甚至把这家模型拖到代走超限判负，但其余桌次照常推进，对局引擎的回合流程不会被任何一个卡住的请求挂起。判负也照旧由代码裁判执行，限流动摇不了胜负归属的权柄。

## 设计取舍

三笔账摆在明面上。其一，为什么不无限退避：锦标赛有排程，对局有节奏，为一家限流厂商等上十分钟，等于把全桌的时间押给它；退避给等待设了边界，边界之外交给兜底。其二，为什么不直接判负：一次 429 反映的是厂商的拥挤程度，不是模型的棋力，因厂商抖动直接判负，天梯的分就失去了含金量。其三，为什么自动而不是手动：挂机场景没有人在场，凌晨的限流若等人来点重试，自动化就名存实亡。

还有一笔隐性账：回喂与重试都是真实请求，都在烧你自己的额度。策略用等待和上下文换成功率，换不来免费——网络环境差的时候挂锦标赛，这笔 token 开销要有预期。

## 边界

三条实话。退避与回喂会拉长那一手的等待时间，对局室里每手延迟的展示不会替你隐藏这个数字，限流严重的厂商一眼就能认出来。长时间严重限流的厂商，代走计数会在名下累积，极端情况真的会被自己的 Key 拖到判负——这不算冤，稳妥起见，办赛前把状态差的那家从名单里摘出去。回喂的上下文只在那一手的处理流程内生效，救得了一手，救不了整晚；整晚的稳定性靠配置页里的厂商选择，中途换 Key 或换厂商不用停赛，配置热读取在下一手就生效。

### 429限流退避一般要等多久

没有固定秒数，看厂商返回的限流窗口与本地策略，具体节奏以仓库实现为准。设计原则是两头不沾：不激进到立刻重发被连续拒绝，不保守到一手棋干等数分钟。对局室里的每手延迟展示会如实反映等待。

### 限流会损坏对局的公平吗

厂商限流对桌上的选手并不均等：被限流的只有那一家。系统的补偿是把失能的后果限制在该玩家名下——它的招由代走接手，计数超限判负，而判负与否由代码裁判说了算，与限流本身无关。

### 能不能提前配置多家厂商防限流

可以，这正是锦标赛挂机的稳妥姿势。85 家目录里多配几家备用，配置带写锁与热读，中途换厂商不用停赛。不过每家厂商各是独立的 Key 与账单，多配几家就多几份额度开销。

### 回喂会不会把上下文越喂越长

不会无限增长。回喂发生在那一手的处理流程内部，喂进去的是上一轮的失败回复，不改变整局的装配方式。代价是多一轮真实请求多一份 token，这个开销换的是那一手的成功率。

429限流退避是一段不太起眼却决定产品下限的代码：它把「模型在线服务会抖」这条现实，翻译成了对局引擎的呼吸节奏。棋力看模型，下限看工程——一局棋能不能稳稳当当走完，靠的正是这类没人叫好的机制。
