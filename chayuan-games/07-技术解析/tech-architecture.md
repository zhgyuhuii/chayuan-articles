# 察元竞技场架构解析：网关、引擎与界面三层

判断一款桌面应用的成色，别急着看界面，先看它怎么分层。察元竞技场架构把这件事做得很干脆：主进程、引擎层、界面层，三层的职责与边界在目录结构上就写得明明白白。这篇按三层职责、进程边界、分层理由的顺序拆开讲。开源仓库 github.com/zhgyuhuii/chayuan-games，MIT 协议，读完再去看目录，应该能一眼对上号。

## 一团浆糊是怎么长出来的

不少 Electron 应用都有同一个病灶：渲染进程里直接发模型请求，规则判定散落在组件里，存档逻辑到处复制粘贴。demo 阶段跑得飞快，欠下的债分三笔。规则没法单独测试，想验证一个吃子判定得先把整个应用跑起来；能力没法复用，想把同一套规则塞进另一个宿主，等于推倒重写；安全边界糊成一团，渲染进程拿着 API Key 想发哪儿发哪儿，一出注入就是 Key 外泄。

察元竞技场架构给出的回答，本质上是对这三笔债各自的清偿方案：规则收进引擎层，请求收进主进程，界面只负责画。

## 三层各管什么

主进程住在 electron/ 目录，管三件事。其一是单实例锁，应用同时只开一份，两份进程抢同一个存档文件这种事故从源头堵死。其二是本机模型网关，所有模型流量从这里单点出口，监听回环地址加随机端口，API Key 只在这一侧出现。其三是 JSON 存档，写入带写锁，运行时热读取，配置改完不用重启，下一手对局就用得上。

引擎层住在 src/arena/ 目录，是整个产品的技术底座：11 款玩法的裁判全是纯逻辑代码，零 IO；对局引擎把裁判、玩家、回合流程串成完整对局；LLM 玩家负责跟各家模型对话、跑出招解析；TrueSkill 评分与开局库也安在这一层。这一层不知道自己跑在 Electron 里还是别的宿主里，也不知道界面上有没有人在看，它只认局面、动作与规则真值。

界面层住在 src/app/ 目录，React 19 加 Vite 7 加 Tailwind 4 的组合，铺出大厅、对局室、天梯、记录、回放、设置六个页面，暗色竞技场风格，中英双语。它消费引擎层的状态与事件，自己不做任何规则判定，也不直接碰网络。

三层怎么协作，跟着一步棋走一遍最直观。你在对局室选好模型开一局，对局请求落进引擎层，裁判的 pendingAction 报出轮到谁、需要什么动作；LLM 玩家把局面陈述与合法动作清单装配成提示，经主进程的网关发给模型；模型回包后，解析链在引擎层完成清洗，动作交给 apply 落到局面；裁判返回的事件流回到界面层，思维链气泡、每手延迟与 token 用量随之刷新。三层的职责在这一步棋里各出现一次，谁也没有越界替谁干活。

## 进程边界划在哪里

Electron 的进程模型天然隔开主进程与渲染进程，察元竞技场架构把这条线用到了实处。模型请求只许从主进程走：渲染进程拿不到 API Key，也摸不到网关的门牌——回环绑定加路径令牌，让同机的其他进程想探进去也难。存档文件同样归主进程独管，写锁保证任何时刻只有一个写入者，JSON 不会被并发写花。

引擎层反而是刻意不设进程边界的一层：它装配在哪一侧，由宿主说了算。这个弹性的回报，在讲同构复用时就能看到。

单实例与存档写锁也是边界的一部分。应用只开一份，存档的写权收在主进程，意味着任何时候都只有一个写入者在动 JSON；界面层读到的配置永远是主进程吐出的最新一份。这套安排让「改配置下一手生效」成为可能，也避免了两份对局互相覆盖棋谱的尴尬。

## 为什么这样分层

三个理由，一个比一个现实。

可测试性。11 款裁判是纯逻辑真值判定，不碰文件、不发请求，vitest 可以对着边界条件猛测：气的计算、劫的循环、牌型比较，毫秒级跑完一轮。规则一旦和 UI、网络搅在一起，这种测试密度根本铺不开。

跨宿主复用。察元AI OS 内置了同款竞技场，引擎层与独立桌面版逐字节同构，还有一道叫 sync-check 的护栏盯着，两边稍有出入就报警。没有干净的引擎层，这种「同一套规则、两个宿主」的承诺无从兑现。

安全收口。流量单点出口意味着审计面只有一处：请求从哪来、发到哪去、429 限流怎么退避，全在网关一侧看得见。界面层从头到尾不需要知道 Key 的存在。

## 真实边界

分层不是免费的，几笔账要认。存档选 JSON 文件加写锁，换来可读、可导出、可热读，代价是数据量大了之后的检索效率不如正经数据库——版本 0.1.0 阶段这是合理取舍，可你要是挂机跑上几百局锦标赛，记录页的打开速度就得看机器了。引擎层与界面层之间走事件同步，锦标赛批量推进时，界面上每手延迟与 token 用量的刷新有自己的节奏，不是逐毫秒跟手。另外 React 19 与 Vite 7 都是比较新的主版本，个别老设备上暗色界面的渲染表现以实机为准。

### 引擎层为什么放在 src 目录而不是主进程里

结论先说：为了让规则脱离宿主独立存在。src/arena/ 是一套纯逻辑代码，Electron 只是它众多可能宿主中的一个，察元AI OS 内置版就是另一个。塞进主进程，规则就与 Electron 的生命周期绑死，逐字节同构这种事也就无从谈起了。

### 界面层能不能绕过网关直接调模型 API

设计上不允许。所有模型流量走主进程的本机模型网关单点出口，界面层接触不到 API Key。这样限流退避、协议转换这些横切逻辑只需写一遍，Key 的暴露面也被压到主进程一处。

### 改了模型配置需要重启应用吗

不用。配置写入带写锁、运行时热读取，改动在下一手对局生效。但已经在等待模型响应的那一手不会中途换人，切换从下一个动作开始。

### 接一款新玩法要动多少地方

主战场在引擎层：按同一套裁判契约实现新玩法的规则，再挂进对局流程，网关与界面不用大动。界面消费的是引擎抛出的状态与事件，契约一致，呈现层就能复用。当然，棋盘渲染、布阵交互这类玩法专属的界面细节仍要单独做，军棋暗棋的两击与拖拽落子就是例子。

察元竞技场架构的三层划分，说到底是一个朴素的工程判断：规则要能独立被测试，请求要能独立被收口，界面要能随时被重画。0.1.0 的代码规模不算庞大，但边界意识已经长在目录结构里了。读代码的人顺着目录走，就能把这套设计再走一遍。
