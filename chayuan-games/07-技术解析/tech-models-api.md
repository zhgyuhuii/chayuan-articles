# 双口径模型列表：测试连接与获取模型的设计

设置 ＞ 模型配置里有一对按钮：「测试连接」与「获取模型」。多数人点完就走，很少想过它们背后的设计有多拧着来：一个用 GET 校验、失败会悄悄回退；一个用 POST 实拉、失败就明着失败，绝不回退。这对双口径模型列表为什么要长成两个脾气，是这篇要拆的事。

## 两个按钮，两种诉求

配模型的场景里藏着两个不同的诉求。一是验证：这家厂商的 Key 与端点通不通，能不能用。二是枚举：这个账号底下到底有哪些模型可勾。两个诉求看着相近，对失败的处理要求却是相反的——验证要宽容，错杀会让能用的配置进不了门；枚举要严格，掺假会让模型库被脏数据污染。双口径模型列表的分歧，正是从这两种相反的要求里长出来的。

## 测试连接：宽容的校验

「测试连接」走 GET /v1/models，用一次轻量请求校验 Key 与端点的连通性。它的失败处理是静默回退：请求没通过，界面不弹错把你拦在半路，而是退回手填模型列表的路子，让你把模型 id 自己敲进去继续用。

宽容的理由在厂商端。各家对模型列表接口的支持参差不齐：有的中转不实现 GET 列表，有的本地推理服务这个接口返回得含糊，接口缺失或返回怪异，不等于 Key 无效，更不等于模型调不通。校验动作的目标是把明显不可用的配置拦在门外，而不是给连通性出一份法律文书——拿一次列表请求的成败给整条链路判死刑，误伤率太高。静默回退把判断权交还给你：接口不给力，手填照样玩。

配合 85 家厂商目录，这颗按钮的体验是顺的：点选厂商，baseUrl 与默认端点就位，你只需要填 Key，点「测试连接」即可。失败时静默回退意味着验证永远不阻塞开局，最坏情况是你手敲一个模型 id，十几秒的事。

## 获取模型：严格的实拉

「获取模型」走 POST /v1/models，用当前输入框里未保存的 baseUrl 与 Key，向厂商实拉该账号可用的模型全列表。严格实拉，不回退：拉不到就明说，绝不拿一份默认清单或缓存数据糊弄你。返回的是裸模型 id，界面上勾选之后才入库。裸 id 不带说明也有好处：没有厂商包装的营销描述，你看到的名单就是账号权限的真实边界，能用什么、不能用什么，列表说话。

严格的理由同样在用途上。这份列表是用来勾选入库的，是后续对局选模型的候选池，错一条、少一条、多一条都会变成你模型库里的长期杂质。给不出真实清单，宁可失败让你看见，也不编一份像样的替身。用未保存的输入去拉，是体贴也是逻辑必然：你刚改完 Key 或端点还没保存，要验证的就是眼前这份新配置，先保存再拉的多余步骤没有存在的理由。

勾选入库之后的去向也顺带说清：入库的模型 id 进入对局与锦标赛的选人列表，人机局挑对手、机机观战批量选模型、锦标赛圈参赛名单，用的都是这份库。列表拉得准，后面每个环节的选择就都建立在真实可用的候选上。

## 为什么一个 GET 一个 POST

两种口径并存，源头是厂商侧的现实：模型列表这个能力，不同服务开放在不同的语义下，有的按 GET 响应，有的按 POST 响应。双口径模型列表把两种都备上，测试连接用 GET 校验，获取模型用 POST 实拉，各取所需。你不需要理解这些差异也能正常用——按钮文案已经把语义写清了；但知道内部逻辑，出问题时能自己判断该查哪一头。顺带一提，GET 与 POST 的选择是产品替你做的，你感知到的只是两颗按钮文案的差异，协议层的琐碎被挡在了界面之下。

两颗按钮也不是替代关系，更像一急一全。急用时「测试连接」几秒给结论，失败也能开局；从容时「获取模型」一步把全列表拉下来勾选，顺带完成对 Key 的一次强验证。头一回配某家厂商，先测连后实拉是稳的顺序；熟练之后直接实拉也行。这套设计还照顾了一个现实：同一台机器上你多半不止接一家厂商，85 家目录里点选几家，每家各自测连、各自拉列表，配置互不干扰。

## 边界

几条实话。获取模型严格不回退，意味着厂商端不支持 POST 列表时它就是会失败，这不是 bug，是设计上拒绝给假数据，此时你的路是手填模型 id。拉回来的是裸 id 清单，不带能力说明与档位信息，哪个模型擅长下棋、哪个遵守协议的习惯好，得自己上桌打几局才知道。中转端点（OneAPI、NewAPI 一类）返回的列表可能是聚合后的结果，id 与实际可用路由未必一一对应，勾选后建议先打一局人机验证。另外，测试连接的静默回退可能让配置问题延后暴露——连接测试过了、实际对局才发现端点不给力，这种时序差要有心理预期。最后补一句数据位置：拉取与测试的请求都从本机网关出口直达厂商端点，拉回来的清单只落在你的本机配置里，不经过任何第三方。

### 双口径模型列表为什么不用同一个接口

因为厂商侧的现实就是两种语义并存，GET 与 POST 各有一批支持者。与其强行统一后在个别厂商身上翻车，不如按用途拆开：校验走宽容的 GET，实拉走严格的 POST，失败策略各自匹配用途。

### 获取模型失败是不是说明 Key 无效

不一定。它只说明这份未保存的输入没能实拉到列表，可能是端点不支持 POST 列表、可能是网络问题、也可能 Key 确实不对。想分辨，用「测试连接」再做一次轻量校验，两个结果放在一起看，就能圈出问题的范围。

### 手填模型 id 靠谱吗

靠谱，这是被静默回退正式支持的主路径。模型 id 按厂商文档或控制台里的名称填，填对就能用。「获取模型」的存在只是省去查文档的功夫，不是手填的前置条件。

### 中转端点适合用哪颗按钮

建议两颗都用。「测试连接」先确认中转通不通，「获取模型」再拉聚合列表；中转返回的 id 可能与实际路由有出入，勾选后先打一局人机验证，别急着把整份列表排进锦标赛。

一对按钮背后的分歧，本质是对失败的态度分歧：验证环节的错误应该便宜、可绕过；枚举环节的错误应该昂贵、立刻暴露。双口径模型列表把两种态度分别落实到了接口选择与回退策略上。这种小事上的较真，往往比大功能更能看出一个产品的工程性格。
