### 为什么这样设计

一层一层看：不明白「模型代理」是什么、向导和文档里反复提到的 52581 是干嘛的。web/docker 形态：代理运行在 dsh 所在服务端机器，127.0.0.1:52581 指向服务端本机回环。好处：以后换模型、换厂商，智能体配置里的地址都不用动，只改模型名即可。这套做法谈不上新颖，但胜在稳。

想让某个智能体 / 自写脚本用上本机的本地模型和已配置厂商，但不想逐家配地址和 key。「模型代理的作用是什么？为什么只配一个地址？」这不是玄学，是写进文档里的行为。

「模型代理在哪里开启？怎么确认它正常运行？」本地模型（llama-server 实例）──┐。单看没什么，连起来看就有意思了。

### 一个反直觉的细节

统一命名空间：本地模型叫 local/<模型id>，云端厂商模型叫 <厂商id>/<模型名>（如 local/qwen3.5-4b-q4km、deepseek/deepseek-chat）。├─ 模型代理 127.0.0.1:52581 ─ 对话 · 知识库 · 智能体。云端厂商（厂商路由转发）───────┘。这个数字记得住，用的时候就不慌。

调谁都走同一个地址、同一套 OpenAI 兼容协议。具体到操作面，PDF 和扫描件这条在手册里写得很细。这个细节不影响功能，但决定你愿不愿意一直开着。

它真正值得说的不是功能列表，而是面对麻烦情况时的处理方式。用察元OS模型代理细看的人迟早会遇到这一刻：功能谁都会堆，难的是出问题那一刻的表现：是悄悄降级让你无感，还是直接报错让你干等，或者干脆丢数据。这三种选择的差距，用一次就知道，而这一次的经验比十篇导购文都可靠。

一个绕不开的问题：能从局域网其他电脑访问这个代理吗？ 浏览器里的「验证」URL 访问的是你自己的电脑而非服务端，应以代理设置页显示的状态与服务端可达性为准。

### 工程上的取舍

② 不通则到 设置 模型 看顶部健康灯，本地模型服务停了代理随之不在，恢复服务即可。转发云端时真实厂商 key 由代理在本机凭证库（~/.dsh/.credentials.yaml）里解析并只在服务端注入，调用方永远接触不到。免 key 直连：代理对鉴权层一律放行——不带 key、带任意值都能调用。这一点挺难得，很多同类产品只在宣传页里讲。

Authorization 头仅用于审计归因（恰好匹配在册虚拟 key 记智能体名，其余记 anonymous）。真实厂商 key 只在代理服务端解析，永不出本机凭证库。

发一次真实调用（上面 curl 示例换成自己的模型名）：正常返回聊天 JSON；调未运行的本地模型首次会有加载等待。代理未运行时显示红点 + 「代理未运行」，且服务地址区顶部只显红字「代理未运行」。别嫌它啰嗦，啰嗦的地方正是容易翻车的地方。

### 这套设计的代价

没有只有好处的设计。右侧「一键重应用」按钮：重启代理 listener（端口重读持久化值，仍固定 52581），改动路由后如遇异常可点它，绿色提示「代理已重应用」。打开 设置 模型，左栏「本地模型」组（默认展开）里点「模型代理设置」。页面自上而下分区：运行状态 服务地址 虚拟 key 被代理模型 厂商路由 调用审计。
